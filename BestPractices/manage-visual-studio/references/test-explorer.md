# Test Explorer backend

CLI remains the default for existing test tools. Opt into the IDE backend with `backend: "test-explorer"`; an unavailable IDE API never silently starts CLI tests. The adapter probes Visual Studio 18 Test Window contracts at runtime. Other versions or changed API shapes can report unsupported.

Build the selected test project first, then call `test_discover(projectName, backend: "test-explorer")`. Initialization is automatic; discovery can require time while IDE adapters update. Responses contain at most 200 cases. Use a returned `testId` as `filter: "id:<native GUID>"`, or an exact `fullyQualifiedName`. CLI filter expressions and retained result fingerprints are not IDE execution selectors. Ambiguous multi-source/framework selections are rejected.

Run a selected case with `test_run` or `test_run_and_get_results`, preserving the explicit session route. For `test_run`, inspect the single result directly. Use `test_run_and_get_results` for batches and check its run ID and outcome. Use `test_results_page` with the exact runId for bounded failure evidence and history.

Parameter selection depends on the backend. `projectName` is required for Test Explorer and for `test_debug` on either backend; CLI discovery and runs may omit it. CLI `filter` values are `dotnet test --filter` expressions, such as `FullyQualifiedName=MyTests.CustomerTests.Search`. Test Explorer fully qualified names are case-sensitive exact matches and can select multiple parameterized cases. To target one discovered case, use `id:<testId>`; an ID that cannot map uniquely to an IDE execution selector is rejected. Omitting `filter` runs all cases in the selected scope, subject to the source/framework ambiguity checks.

`test_debug` always requires a non-empty `filter` and an idle debugger. CLI debugging also requires `framework`, such as `net10.0`; an exact `FullyQualifiedName=...` expression targets a method, while broader expressions may debug multiple tests. For Test Explorer debugging, build separately, leave `noBuild` false, and omit `configuration` and `framework`. The IDE uses its project configuration and the selected discovered source/framework. `attachTimeoutSeconds` applies only to CLI debugging.

Canceling an active Test Explorer tool call requests cancellation of that call's owned IDE run through a separate recovery RPC. Cancellation targets only that IDE request. A canceled wait alone is not confirmation: inspect the returned terminal outcome. An unknown outcome requires reconciliation; never repeat a mutation just to recover a lost response.

For debugging, set source breakpoints before `test_debug(projectName, filter, backend: "test-explorer")`. The IDE selects the discovered native cases and launches debugging. The response reports `outcome: "accepted"` and a runId; it does not claim a verified process attachment. Wait for `debug_status` to report running or paused before `debug_wait_for_break`, verify the intended test-method stack, then use ordinary debugger tools. Failed assertions can cause another exception pause depending on IDE settings; inspect it before continuing. CLI-only framework/build options do not apply. Read retained results with `test_results_page(runId)` after the IDE run finishes. While it is active, the same call reports its current outcome. Confirm before stopping or terminating a target unless cleanup is already authorized.

IDE run/result state belongs to the current VS session. Broker restart does not replay it, and VS restart loses in-memory result history. Reconcile the exact session, debugger, and known runId before submitting new work.
